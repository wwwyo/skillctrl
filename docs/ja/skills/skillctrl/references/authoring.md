# skill を作成・改善する

新しい再利用可能な skill を作る、取り込んだ skill を意図に沿って調整する、
変更後の振る舞いを確認する場合に、この手順を使う。
この手順だけで進められ、`find-skills` や `skill-creator` を別途導入する必要はない。

## 具体的なワークフローを整理する

会話とリポジトリから、作業内容、起動条件、制約、ツール、期待する出力、完了条件を整理する。
結果に影響し、手元の情報から判断できないことだけを質問する。
仮の作業向けに一般論を作るより、すでに使われ、修正してきたワークフローを優先する。

再利用と新規作成を比較している場合は、既存の skill を探す。
作成を明示的に依頼されている場合は、公開 skill の検索を必須にしない。
同じ作業を担当するローカルの skill があれば再利用し、改名を依頼されていなければ名前を保持する。
本格的なベンチマークや description の最適化は、依頼された場合に別の評価作業として行い、
小さな編集のたびに要求しない。

## パッケージを書く

対象リポジトリで使う skill は `.agents/skills/<name>/SKILL.md` に書く。
配布用のパッケージは、取得元リポジトリの配布用配置、例えば
`skills/<name>/SKILL.md` を使い、別の場所への導入を検証する。
公開する原本のディレクトリと、実際に使う導入先を混同しない。
未導入のパッケージに `record` を実行しない。

Agent Skills の形式を使う。

```markdown
---
name: example-workflow
description: "例となる成果物を作成し、確認する。ユーザーが成果物を依頼したとき、このワークフローを指定したとき、出力の修正を依頼したときに使う。"
---

# ワークフローの例

求める結果、それを作る手順、確認方法を記述する。
```

`name` は直上のディレクトリ名と一致させる。
1〜64 文字の小文字英字・数字・ハイフンを使い、先頭・末尾・連続するハイフンは避ける。
description は 1,024 文字以内とし、作業内容と起動条件を含める。
`: ` など、YAML の構文に影響する文字を含む文字列は引用符で囲む。
配布に必要な場合は、ライセンスとツールの互換性情報を追加する。

具体的な既定値、実際のツールコマンド、判断する箇所、観察可能な完了条件を含め、簡潔な手順を書く。
自明でない制約は理由を説明する。agent がすでに知っていることを繰り返したり、
ユーザーが認めた通常の操作に承認を要求したりしない。
公開パッケージに credential や個人用の設定を入れない。

長い作業固有の説明は `references/`、再利用できる決定論的な補助処理は `scripts/`、
テンプレートは `assets/` に置く。
各リソースには、読む・実行する条件を添えて `SKILL.md` からリンクする。
入口は 500 行未満にし、取得元リポジトリから別の場所へコピーしても使えるようにする。
非公開のパスや、別途導入する補助 skill に依存しない。
形式について判断が必要なら https://agentskills.io/specification を参照する。

取り込んだ skill には、カスタマイズの要件も
`.agents/skillctrl/intents/<name>.md` に書く。
手書きの skill は upstream 管理の対象外であり、上流の登録も記録済み hash も不要。

## 検証して改善する

主なワークフロー、起こりそうな境界条件、似ているが skill を起動すべきでない依頼を含め、
現実的な prompt を 2〜3 個選ぶ。実行前に成功条件を定義する。
繰り返し評価する価値があるパッケージでは、再利用できるケースを `evals/evals.json` に保存する。

frontmatter、相対リンク、コマンド例、必要なツール、同梱 scripts を確認する。
その後、使い捨ての場所か、作業を認められた workspace で代表的なタスクを実行する。
ソフトウェア導入・公開・実環境の設定変更を伴う操作には、fixture や読み取り専用の計画を使う。
実際の導入を検証したと報告せず、その検証範囲を明示する。

独立した runner を使え、依頼が評価を含む場合は、同じケースを skill あり・なし、
編集の場合は旧版と新版で比較する。
最終的な文章だけでなく、観察可能な結果と、実際に従った指示を確認して採点する。
静的な確認や比較対象のない 1 回の実行だけから、改善効果を測れたと判断しない。
誤って起動するケースは、実行内容の正しさとは分けて確認する。

具体的な失敗を直し、役に立たなかった指示を削除し、影響するケースを再実行する。
検証は変更の規模に合わせる。コマンドの修正なら、新しいワークフローほど広い検証は不要。
何を試したか、何が未検証かを報告する。

`.agents/skills/` に導入した upstream 登録済み skill を検証したら、ディレクトリ全体を確認し、
その作業先で `skillctrl record <name>` を実行して、意図した内容の hash を記録する。
手書きの skill は、検証すれば編集が完了し、追加の hash 記録は不要。
配布用の原本パッケージは、その原本の差分を確認する。hash の記録は別の導入先で行う。
commit と公開は、ユーザーがすでに与えた指示に従う。
